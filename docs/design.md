# 设计方案：Pi 项目研发编排 Skill

## 一、项目定位

本仓库交付一个轻量 Pi Skill：用户在具体 Git 项目中与 Pi 持续讨论方案；Pi 委派
Claude Code（默认）或用户指定的 Cursor 做源码调查、正式编码和必要复审；编码
结束后，Pi 独立检查代码、重跑测试、在本机运行当前候选并从正式入口完成业务验收；
候选通过后，再分别获得 commit、push 和部署授权，通过 Git 将固定 SHA 更新到
目标机器并验证。

项目方案、规则、部署方法、任务书和进度只保存在项目仓库。Obsidian 中的探索
记录不作为开发或验收真源。

## 二、最终只解决四件事

### 1. 指挥编码 Agent

- 默认 Claude Code；用户明确指定时 Cursor。
- 方案转成有 Risk、Scope、Verify 的任务书后再委派。
- 执行器失败时如实说明，不静默重试或换人。
- 只有同一执行器、同一任务、Git 基线未变化时续接原会话。
- 同一工作区同时只允许一个写权限编码 Agent。

### 2. 讨论方案并核对落地

- 先讨论业务和技术方案；源码不明时委派只读调查。
- 方案写入项目 `docs/` 并由用户确认；确认方案不等于授权编码。
- 编码后 Pi 对照方案和完整 diff 检查，偏差交原 Agent 窄修。
- Pi 默认不直接编写正式业务代码、正式测试、迁移和部署配置。

### 3. 自动化测试与本机候选运行验收

- 编码 Agent 先执行相关测试，Pi 再亲自运行必要测试并检查是否有跳过或放松。
- 改变运行行为的候选必须重新构建/安装，按项目真实方式在本机启动，并从正式
  入口走核心黑盒业务场景，核对最终结果和日志。
- 统一的是验收目标，不强制 Docker。容器、原生进程、正式制品、干净安装环境或
  混合方式都可以。
- 单元测试、PID、容器 running、单独健康接口或 Agent 自报均不能单独证明完成。
- 纯文档可免本机运行验收，但任务书和交接要写明理由；环境不具备时写“受阻”。

### 4. 通过 Git 部署到目标机器

固定链路：

```
本机候选验收通过
→ 用户授权 commit
→ commit
→ 用户授权 push
→ push 并核远端 SHA
→ 固定待部署 SHA
→ 用户授权指定机器部署
→ 目标机检查干净工作区
→ Git fetch，确认远程分支头等于批准 SHA，再 git pull --ff-only
→ 确认 HEAD 等于批准 SHA
→ 构建或重启
→ 健康检查和业务验证
→ 更新 HANDOVER
```

禁止 rsync、scp 复制项目代码、docker cp、压缩包覆盖、手工单文件替换和其他绕开
Git 的交付方式。工作区不干净、分支不符、无法 `git pull --ff-only`、远程分支头或
目标机 HEAD 与批准 SHA 不符时停止。
回滚必须重新获得授权。

## 三、角色分工

| 角色 | 职责 |
|---|---|
| 用户 | 业务方向、方案确认、编码授权、执行器切换、commit、push、部署和生产访问授权 |
| Pi | 讨论、任务、执行器编排、diff、测试、本机业务验收、复审、Git 部署和交接 |
| Claude Code | 默认执行器：调查、正式编码、测试、窄修 |
| Cursor | 用户指定时编码，或作为独立复审器 |
| 项目仓库 | 方案、规则、部署方法、任务书和真实进度的唯一真源 |

## 四、项目仓库约定

```text
项目根目录/
├── AGENTS.md
├── CLAUDE.md
├── HANDOVER.md
├── docs/
│   ├── architecture.md
│   ├── deployment.md
│   ├── decisions/
│   └── milestones/
└── .pi/
    └── tasks/
```

- `AGENTS.md`：长期技术栈、测试、本机运行和授权规则。
- `CLAUDE.md`：编码 Agent 入口，要求读取规则、方案、交接和当前任务书。
- `HANDOVER.md`：当前真实状态、验证、Git、部署、阻断和会话信息。
- `docs/`：方案、架构和决策的唯一真源。
- `docs/deployment.md`：本机候选验收和目标机 Git 部署的可执行方法。
- `.pi/tasks/`：当前任务不可变任务书，至少包含 Risk、Scope、Verify。

## 五、完整工作流

1. 进入项目，读取控制文件和 Git 真实状态。
2. 与用户讨论目标、方案、范围和验收场景。
3. 必要时委派 Claude Code/Cursor 只读调查，前后核对工作区未改。
4. 把方案写进 `docs/`，等待用户确认和编码授权。
5. 生成任务书，提前固定测试与本机黑盒验收方法。
6. 默认委派 Claude Code 编码；Cursor 仅按用户指定编码。
7. Pi 检查完整 diff，重跑自动化测试。
8. Pi 从当前工作区重建候选，在本机启动并执行业务验收。
9. 失败则保留证据：方案问题回讨论，实现问题交原 Agent 窄修，环境问题标受阻。
10. 普通任务本地收口；关键任务增加更完整测试、边界场景和至少一路独立复审。
11. 本机候选通过后，分别申请 commit、push 和部署授权。
12. 目标机只通过 Git 更新批准 SHA，构建/重启后做健康和业务验证。
13. 更新 `HANDOVER.md`，保持各状态独立、可追溯。

## 六、测试和复审分档

不使用复杂的 L1/L2/L3 矩阵，只分两类：

| 类型 | 最低要求 |
|---|---|
| 普通任务 | 相关测试 + Pi 完整 diff；改变运行行为时做本机候选业务验收 |
| 关键任务 | 普通任务全部要求 + 更完整受影响测试 + 关键失败/边界/恢复场景 + 至少一路独立复审 |

权限、认证、资金、删除/生产数据、并发/锁/状态机、数据库迁移、安全边界、发布、
灰度、回滚、恢复和核心共享契约属于关键任务。纯文档可明确免除运行验收。

## 七、本机候选验收原则

- 默认使用 `127.0.0.1`、测试数据库、合成数据、独立端口和临时资源。
- 数据库使用与目标环境一致的类型和主版本；MySQL 项目不得拿 SQLite 代替。
- 当前候选必须重新构建，不能复用来源不明的旧镜像、二进制或前端制品。
- 前端通过真实浏览器动态验收；CLI/SDK 要验证打包安装后的公开入口。
- 不读取生产凭证，不连接生产数据库或生产服务。
- 代码、测试、配置、依赖或构建输入变化后，旧验收结果失效。
- 安装全局软件、修改系统配置、SSH、外部环境或真实凭证仍需另行授权。

## 八、部署原则

每个项目维护 `docs/deployment.md`，写清 Git 仓库、分支、目标机、绝对路径、依赖、
构建、重启、健康、业务验证、版本确认和回滚。不得写真实凭证。

commit、push、部署和回滚分别授权。部署身份必须是已推送的完整 commit SHA。目标机
工作区脏、分支错误、远程分支头不是批准 SHA、不能 `git pull --ff-only` 或 HEAD
不符时 fail-loud，
不覆盖、不清理、不强推、不自行换版本。

## 九、Skill 结构

```text
project-development-orchestrator/
├── SKILL.md
├── references/
│   ├── development-workflow.md
│   ├── claude-code.md
│   ├── cursor.md
│   ├── testing-and-review.md
│   └── git-deployment.md
├── templates/
│   ├── AGENTS.md
│   ├── CLAUDE.md
│   ├── HANDOVER.md
│   ├── task.md
│   └── deployment.md
└── scripts/
    ├── run-claude
    ├── run-cursor
    ├── workspace-write-lock.js
    ├── workspace-write-lock.test.js
    └── fake-executor.test-fixture.js
```

两个 wrapper 只处理 CLI 参数差异、工作目录、模式、模型、结构化结果、
session_id、原始输出证据，以及同一真实工作区的跨执行器写互斥；不管理状态、
授权、测试、部署、任务或 Token，不自动 fallback/重试。`workspace-write-lock.js`
实现按工作区真实路径划分的写锁，供 `run-claude`/`run-cursor` 在 `code` 模式下
共用：同一工作区同一时刻只允许一个有写权限的编码 Agent 持有锁，只读调用
（`investigate`/`review`）不占锁，不同工作区互不阻塞；`workspace-write-lock.test.js`
覆盖同工作区互斥、跨工作区不互斥、只读不占锁、持锁进程退出/崩溃后的锁回收等
场景。

## 十、明确不建设

不建设 Pi 全局 AGENTS/settings、Project Guard Extension、授权数据库、命令拦截器、
自研敏感文件平台、自动测试/范围验证平台、长任务调度数据库、并发锁系统、证据
归档平台、Token/费用平台、Hermes-Pi A/B 系统或统一 Docker 平台；不与 Obsidian
形成双真源，不恢复已删除的平台代码。

## 十一、完成标准

静态产物完成后仍不等于整体签收：先全量通读和测试，随后安装 Pi 和 Skill，在一个
新项目中真实走通“讨论 → 调查 → 授权编码 → Agent 编码 → Pi diff/测试 → 本机候选
启动和业务验收 → 复审/窄修 → HANDOVER 续接”；有合适测试机器时，再分别授权
commit、push 和 Git 部署，验证固定 SHA、构建/重启、健康与业务场景。发现缺口只
修对应环节，不扩建平台。
