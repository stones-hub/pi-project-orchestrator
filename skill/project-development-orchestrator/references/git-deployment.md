# 通过 Git 部署到目标机器

## 前提

- 本机候选验收已通过，且验证对应当前代码候选。
- 项目已维护 `docs/deployment.md`，其中没有真实凭证。
- commit、push、部署分别获得明确授权；部署授权指出项目、机器、分支、commit
  SHA、构建/重启和验收范围。
- 待部署代码已经 push 到批准的远程分支，并冻结具体 SHA；不用 `latest`、模糊
  分支状态或未提交工作区作为部署身份。

## 1. commit

申请授权前向用户展示：拟提交文件、diff 摘要、自动化测试和本机运行验收结果、
拟用 commit message。获批后只提交批准范围，并记录完整 commit SHA。未获授权不
执行 `git add` 或 `git commit`。

## 2. push

申请授权前展示：本地 SHA、目标 remote、目标分支。获批后 push；再读取远端分支
状态，确认远端确实包含该 SHA。push 成功不等于部署授权。

## 3. 部署授权

向用户明确展示并确认：

- 目标机器及连接别名；
- 项目绝对路径；
- remote、部署分支和固定 SHA；
- 将执行的 fetch/更新、依赖、构建和重启命令；
- 健康检查、业务验证和版本身份确认；
- 失败时停止点及文档中的回滚方案。

授权内容有歧义时先澄清，不把“部署一下”扩展到未说明的生产访问或回滚。

## 4. 目标机部署前检查

连接目标机后依次确认：

1. 进入 `docs/deployment.md` 指定的项目绝对路径；
2. 目录是预期 Git 仓库，remote 与部署文档一致；
3. 当前分支符合批准的部署分支；
4. `git status --porcelain` 为空；
5. 批准远程分支的分支头正是批准 SHA，而不只是历史中包含该 SHA；
6. 当前提交可以通过 `git pull --ff-only` 安全更新到批准 SHA。

任一失败立即停止。不得覆盖目标机改动、强推、`reset --hard`、清理未提交文件，
也不得自行改分支或部署另一个 SHA。

## 5. Git 更新与身份核对

按项目文档先执行 `git fetch`，再次确认远程分支头等于批准 SHA，再执行
`git pull --ff-only`。更新后读取目标机完整 `HEAD`，必须等于用户批准的 SHA；
不相等就停止，不执行构建或重启。

代码传递只走 Git。明确禁止：

- `rsync`；
- `scp` 复制项目源码或构建代码；
- `docker cp` 注入代码；
- 临时压缩包或手工单文件覆盖；
- 其他绕开批准 Git 历史的方式。

SSH 仅用于在目标机执行批准的 Git 和部署命令，不用于复制项目代码。

## 6. 构建、重启和验证

严格执行 `docs/deployment.md` 已确认的命令：

1. 安装必要依赖；
2. 构建当前 SHA 的制品；
3. 重启指定服务；
4. 等待业务就绪；
5. 健康检查；
6. 从正式入口完成业务验证；
7. 核对实际运行版本身份仍为批准 SHA。

命令退出码 0、服务 active、容器 running 或健康接口成功，都不能替代业务验证。

## 7. 失败与回滚

- 任一步失败立即停止后续动作，保留错误和目标机当前状态，明确失败在哪一步。
- 不把超时、断连或结果不明写成成功或确定失败；先用只读方式核对实际状态。
- 不自动重复部署，不自动执行破坏性恢复，不擅自修改目标机文件。
- 根据 `docs/deployment.md` 提出具体回滚目标和命令；回滚是新的外部变更，必须
  再获用户明确授权。
- 回滚后也要核对版本身份、健康和业务结果；任一失败如实报告。

## 8. 交接

更新 `HANDOVER.md`：已提交 SHA、已推送 remote/branch、部署授权范围、目标机、
目标机实际 HEAD、构建/重启结果、健康检查、业务验证、生产验收人/标准，以及
所有受阻或结果未知项。不得用“已部署”代替这些分项事实。
